Guides / Room lighting

Light your first room

Wire one room’s lights to the room lighting controller, let motion and wall switches ask it for light, and add a circadian lighting policy for brightness and colour temperature over the day that leave a person’s own change alone.

Before you wire it

One room lighting controller owns one room’s lights. In the palette it is home-room-lighting-controller; on the canvas it shows as “lighting controller”, or “<area> lighting controller” once you give it an area. It is the only node that sends commands to those lights. The policies in front of it (motion, wall switches, activities) send it requests, called intents, and never command a light themselves.

  • Lights you reach over MQTT. Each light needs a topic it reports its state on and a topic it takes commands on, for example a Zigbee2MQTT light’s zigbee2mqtt/<device> and zigbee2mqtt/<device>/set, where <device> is the light’s name in Zigbee2MQTT. The controller speaks the Zigbee2MQTT light payload: state ON or OFF, with brightness and color_temp.
  • An MQTT broker node in Node-RED that reaches the same broker as your lights.
  • Node-RED 5.0.0 or newer and Node.js 24 or newer.
  • A file context store (recommended). Without one, a restart or a redeploy makes the room forget which lights a person set, and a motion node counts the room as vacant from then.

To add the file context store, set this in settings.js in your Node-RED user directory, then restart Node-RED:

settings.js · keep node context on disk
contextStorage: {
    default: { module: "localfilesystem" }
},

The file store writes changes to disk every 30 seconds by default, so a change made just before Node-RED stops can still be lost. The README’s recommended setup lists what each node forgets without it.

Home Assistant is optional.

The room works with no Home Assistant at all. If you use it, it is a view and a control panel: its switches send MQTT messages the controller acts on, and the controller still commands the lights directly. See Home Assistant.

Wire the room

Start from the example: in the Node-RED editor, Import → Examples, then Room lighting. It wires the policies into the controller, with inject nodes standing in for your sensors and a Debug node standing in for MQTT out. Replace those with your own inputs and broker.

Room connections

The motion and switch inputs have their own guides: Motion and occupancy and Wall switches. In the example both policies light the target main; their target names must match the controller’s.

  1. Name the room’s lights.

    Set Targets JSON on the controller. Each light needs an id (the name the policies use), a stateTopic and a commandTopic; ids must be unique.

  2. Send commands out unchanged.

    Wire the controller’s output straight to MQTT out on the same broker, with the MQTT out topic left empty so each command goes to its light’s command topic.

  3. Feed the lights’ reports back.

    Add an MQTT in node on each light’s state topic and tag what it receives as an observation before it reaches the controller. The incoming topic must equal the target’s stateTopic.

  4. Watch the command topics.

    Add an MQTT in node on each light’s command topic, tagged command-observed. This is how the controller tells its own commands from someone else’s.

  5. Send a startup message.

    Keep the example’s “room startup” inject, which fires once 3 seconds after a deploy, so the MQTT broker node has usually connected first.

MQTT in (state topic) → function → controller · tag a light report
msg.lighting = {kind: "observed"};
return msg;
MQTT in (command topic) → function → controller · tag a command
msg.lighting = {kind: "command-observed"};
return msg;

Retained messages on a command topic are ignored, so only a fresh command counts as someone’s change.

Targets JSON · one Zigbee2MQTT light
[{"id": "main",
  "stateTopic": "zigbee2mqtt/<device>",
  "commandTopic": "zigbee2mqtt/<device>/set"}]
Don’t rewrite the controller’s commands on the way.

The controller watches each command topic to tell its own commands from other people’s, so a function that changes them looks like someone else’s change. A bare ON or OFF that arrives within 5 seconds of one of its own commands with that power, before that command has come back, is taken as its own, and it restyles a light after someone else’s bare ON at most once every 5 seconds. Other rewrites can still be misread.

What the policies send

The policies send msg.lighting intents. You can send the same from an Inject or Function node to try the room before any sensor is wired.

Inject → controller · switch the room’s light on
msg.lighting = {kind: "intent", targets: ["main"], state: "ON", source: "motion"};
return msg;

state is "ON", "OFF" or "TOGGLE"; without targets, the intent applies to every light. When the light is in-control and the room has a style (from a circadian lighting policy), an ON intent without values gets that style, with the Turn-on transition seconds. Otherwise it sends a bare ON.

To ask for a particular level, add values in the package’s own units:

Function → controller · a set level
msg.lighting = {
  kind: "intent",
  targets: ["main"],
  state: "ON",
  values: {brightnessPct: 40, colorTempKelvin: 3000}
};
return msg;

brightnessPct is 0–100 and colorTempKelvin is in kelvin; the controller converts them for a Zigbee2MQTT light to its 1–254 brightness and mireds. brightnessPct: 0 is the dimmest the light goes, not off: send state: "OFF" to switch it off. An intent’s values alone don’t make the light manual; add manual: true for a person’s change, described next.

Values alone don’t count as a person’s change. Your flow decides who a request is from; the controller doesn’t guess. When a request comes from a person, for example a dashboard slider, set person: true (or manual: true) on the intent. The controller then records that a person set the light, and motion’s vacancy OFF leaves it on when the person set it after the room went vacant (see Leave a person’s change alone).

Function → controller · a dashboard slider, from a person
msg.lighting = {
  kind: "intent",
  targets: ["main"],
  state: "ON",
  values: {brightnessPct: msg.payload},
  person: true
};
return msg;

Circadian brightness and colour

Circadian styling is its own node, the circadian lighting policy (home-circadian-lighting-policy). Wire its first output into the room controller, as the example does; one policy can style several rooms, or each area can have its own. Its levels follow its Wake time and Bed time (24-hour HH:MM, default 07:00 and 23:00):

  • they rise to the daytime level over the hour after waking;
  • they stay at the daytime brightness and colour through the day;
  • they wind down to the sleep settings over the three hours before bed, and stay there until you wake.

A bed time after midnight, or a wake time later than the bed time, works. Times are the Node-RED host’s local time; Docker containers default to UTC, so set the container’s TZ if the host should follow a local timezone.

The policy sends the room a style once the flows start, every Restyle interval, and at once when circadian lighting, sleep or the times change. The room restyles lights that are on and under its control, over the Restyle transition, and skips a light that already reports that style. A style is never a request to change a light: it doesn’t switch lights on or off, and it never reaches a light a person set or an activity holds. If the policy stops, rooms stop styling within three intervals.

Inject → circadian lighting policy · switch circadian lighting or sleep
msg.lighting = {kind: "circadian", enabled: false};
// or: msg.lighting = {kind: "sleep", enabled: true};
return msg;

enabled is true or false; anything else is refused with a warning. Sleep mode holds the lights at the sleep settings, whatever the time. To share one wake and bed time across rooms, choose a house schedule as the policy’s Schedule; see House schedule.

A light that only switches on and off can be marked "onOffOnly": true in Targets JSON: it is never sent brightness, colour or a transition, and styles skip it.

From 5.x: migrate every room.

Every room controller saved before 6.0 still has its circadian settings, which moved to the policy, and shows as an invalid configuration until migrated. Add a circadian lighting policy wired into the room, set its fields to the room’s old settings (the room’s edit dialog lists them, field by field), then open the room, click Done and deploy both together. A room that should stay unstyled needs only the last step. See the README’s 6.0.0 notes.

Leave a person’s change alone

Each light has one control state, and a style only touches lights that are in-control:

Control states
StateMeansBack to in-control when
in-controlThe room styles the light with the style it is sent. The default.—
manualA person changed the light: an intent with manual: true, or a command with values seen on its command topic. An intent’s values alone don’t make a light manual.It is switched off, or circadian lighting is switched on.
overriddenAnother owner, such as an activity or a scene, holds the light.Its owner releases it, or the owner or a person switches it off.

A held light ignores motion ON and OFF and owner-less values; it changes only for an intent with an owner, a person (manual: true, person: true, an external command, or a change seen at the light), or a release. The switch policy marks its presses with person: true, so a wall switch always reaches the light. A dashboard acting for a person should set one of these too.

The controller also keeps a light a person set after the room went vacant: motion’s OFF doesn’t switch it straight off. Here “a person” means an intent with manual: true or person: true (the switch policy sends person: true with every press), or someone else’s command seen on the light’s command topic. An intent that only carries values neither makes the light manual nor protects it from motion’s OFF; a flow acting for a person should set manual: true or person: true.

Function → controller · hold lights for an activity, then release them
msg.lighting = {
  kind: "intent", targets: ["main"], state: "ON",
  source: "activity", owner: "film",
  values: {brightnessPct: 25, colorTempKelvin: 2500},
  preserveManual: true
};
// later:
// msg.lighting = {kind: "release", targets: ["main"], owner: "film"};
return msg;

With preserveManual: true, lights a person set are skipped. A release without targets releases all of that owner’s lights; released lights that are on are restyled with the room’s style, over the style’s own transition. The activity lighting controller does this for you in a home theatre.

Check the result

The controller’s status shows whether it has a style and the counts, for example styled · 1 on · 0 manual. The dot is yellow whenever a light is manual; otherwise it is green while it has a style and grey without one. The circadian lighting policy’s own status shows the style it sends, such as day · 80% 4100K, sleep or off.

Read the status
What you seeWhat it means
styledThe room has a style in force from a circadian lighting policy.
unstyledNo style: no policy is wired in, circadian lighting is off, or the last style ran out.
invalid configurationA room saved before 6.0 not yet migrated; see above.
… 1 manual (yellow dot)A person set a light; styles leave it alone.
… 1 overriddenAn owner such as an activity holds a light.

Wire a Debug node to the controller’s output, as the example does. Each command has the light’s command topic, a payload such as {state: "ON", brightness, color_temp, transition}, and msg.lighting_command naming the target and the source that asked for it.

After a restart without a context store,

the room leaves every light as it is: a style restyles a light only once an intent or release names it, someone switches it on with a bare ON, or circadian lighting is switched on. To bring a light that is on back into step, switch circadian lighting on, or let motion or a wall switch name it.
