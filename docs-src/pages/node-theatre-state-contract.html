home-theatre-state-contract1 input · 2 outputshome automation

Requests in. Retained truth out.

Turns non-retained MQTT activity requests into activity intents for the theatre activity controller, and publishes that controller’s state snapshots as retained MQTT topics, with an operational SLO and, optionally, Home Assistant discovery. Home Assistant is only a panel: its activity selector publishes a request, and the theatre does the rest.

In the palette it is theatre state contract under home automation; on the canvas it shows its name, or theatre state contract when unnamed.

Looking for wiring or the full topic list?

Follow Home theatre for the wiring, and the Theatre MQTT contract for every topic and payload.

For a node added from the palette, Area is required only when Base topic is empty. A contract saved before node-based IDs also needs it while discovery is on. The contract in the imported Home theatre activity.json example has neither set, so it is invalid until you set an Area (or a Base topic).

New nodes name their Home Assistant entities after the node (idScheme = "node"), so renaming the area keeps them. A contract saved before that setting has idScheme unset and keeps its area-named entities. That internal marker is set when a node is added from the palette; it is not an editor setting.

MQTT and Home Assistant

Requests arrive on <base>/request and must not be retained. Each controller snapshot is published, retained, topic by topic as it changes, under <base>/: desired, current, phase, transition, failure, readiness, metrics, slo, slo/breach and health/<target>. Each topic is published only when its payload changes, leaving aside the fields that only say when or how long ago something was seen (observedAt, evaluatedAt, and in metrics each target’s observationAgeMs and lastConfirmationMs): a steady activity whose targets keep re-confirming publishes nothing new, so Home Assistant records no change for every refresh. A target’s health therefore keeps the time it last changed, not the time it was last confirmed; a target that stops answering is still shown, as readiness going degraded with the target named stale or no-response in transition. Each startup, and with a Broker each connect, publishes every topic again with the next snapshot, in case the broker lost them. An accepted request immediately publishes desired, phase requested, an empty failure and readiness unknown.

Once the flows start it publishes a retained online on <base>/availability, and offline as it stops. These get through only when this node is redeployed on its own, so also set the MQTT broker node’s Birth message to online and its Close and Will messages to offline, all retained, on the same topic (README Upgrading from 2.x). Payloads and entity details are on the Theatre MQTT contract page.

With discovery on, it announces a Requested activity select and sensors for current activity, phase, readiness, failure, transition latency, operational SLO, an SLO breach binary sensor and one health sensor per target, once the flows start and again at each startup message. Switched off, the next startup message clears them.

Status

The node status reads <activity> · <generation> for the latest request, or waiting for state before one. It is a blue dot after passing on a request, a green dot after publishing, and a grey ring otherwise.
