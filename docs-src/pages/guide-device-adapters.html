Before you wire it

The cover controller (home-cover-controller) is device-neutral. It sends commands as msg.cover_command = {operation, position, requestId, generation, attempt}, where operation is set_position, stop or observe (read the cover now). An Open, close and stop only cover sends open, close, stop or observe. It expects readings back as msg.cover = {kind: "observed", …} and {kind: "availability", online}.

An adapter does the translation for one kind of device, so the controller never needs to know which device it drives. An adapter has no broker connection of its own: device messages arrive from an MQTT in node, and its publications leave through an MQTT out node.

  • The package includes one adapter today: the shelly cover node (home-shelly-cover).
  • A Zigbee2MQTT cover is wired today with function nodes, as in the Cover control.json example. A zigbee2mqtt cover adapter is coming with pull request #156; it is not available yet.
  • Have a broker connection in Node-RED that both the MQTT in and MQTT out nodes use.
  • Either way, the device is commanded over its own MQTT messages, never through Home Assistant.

The controller’s positions are 0 = closed and 100 = open. If your device runs the other way, set Invert positions on the controller.

Wire a shelly cover

The shelly cover node connects a Gen2-or-later relay device in cover mode, over the device’s own MQTT API, with no function nodes. It has one input and two outputs: output 1 goes to the device, output 2 to the cover controller. The covers guide walks through its full wiring; this is the summary.

shelly cover settings
SettingDefaultWhat to set
MQTT topic prefixNone: requiredThe device’s topic prefix: its device ID unless a custom prefix is set on the device. It cannot contain + or #.
Cover ID00, or 1 for a device’s second cover.
  1. Prepare the device.

    Calibrate the cover on the device. Turn MQTT on with Enable MQTT Control (the default); without it the device ignores the commands. Keep RPC status notifications on (also the default) so each change is reported.

  2. Subscribe to the whole prefix.

    One MQTT in node on <prefix>/# (output: auto-detect) feeds the adapter. It reads <prefix>/status/cover:<id>, change notifications on <prefix>/events/rpc, and availability on <prefix>/online. Anything else is ignored.

  3. Wire the loop.

    Controller output 1 to the adapter, adapter output 1 to an MQTT out node on the same broker with no topic set, adapter output 2 back to the controller.

  4. Keep the controller as a position cover.

    Leave Cover as “Takes a position (0 to 100)”. The adapter translates set_position, stop and observe; it does not translate the open and close commands of an Open, close and stop only cover.

No position, no guess.

A cover that is not calibrated, or does not know its position, has no position to report. The controller’s command in hand fails with reason not-calibrated or position-unknown, and no position is sent to an uncalibrated cover.

Wire a Zigbee2MQTT cover today

Until the zigbee2mqtt cover adapter arrives, the Cover control.json example shows the mapping in three function nodes between the controller and your MQTT nodes. Copy them into your flow and put your cover’s friendly name in their topic.

Function nodes in the Cover control example
Function nodeWire itWhat it does
from Zigbee2MQTTMQTT in on the cover’s topic → function → controller inputTurns a state report into msg.cover = {kind: "observed", position, motion, observedAt}. Motion comes from motor_state (opening, closing or stopped); battery and charging status are passed on. A report without a numeric position is dropped.
availability from Zigbee2MQTTMQTT in on the cover’s …/availability → function → controller inputTurns {"state": "online"} or "offline" into {kind: "availability", online}.
to Zigbee2MQTTController output 1 → function → MQTT outSends a position or STOP on the cover’s …/set topic, and a position read on its …/get topic.

These function nodes handle position covers only: keep the controller’s Cover as “Takes a position (0 to 100)”. The example’s fourth function node, pause motion while moving, is not part of the device mapping; it feeds controller output 3 to the motion policy’s pause input.

Coming: the zigbee2mqtt cover adapter

Not available yet: the zigbee2mqtt cover node arrives with pull request #156 and replaces the three mapping function nodes. Its settings are a Base topic (zigbee2mqtt by default) and the device’s Friendly name. It will:

  • take reports from MQTT in nodes on <base>/<friendly name> and its …/availability, and send commands through an MQTT out node, wired like the shelly cover;
  • read motion from motor_state (a pause reads as stopped) or moving;
  • also support covers with no position, with the controller set to Open, close and stop only.

What reaches the device

You send requests such as "open", 60 or "stop" to the controller, as in the covers guide. The controller turns them into neutral commands, which become these device messages:

Controller commandshelly cover, on <prefix>/command/cover:<id>Example “to Zigbee2MQTT” function
set_positionpos,<0-100>{"position": <0-100>} on …/set
stopstopSTOP on …/set

msg.cover = {kind: "startup"};
return msg;

On startup the controller reads the cover again rather than trusting old state, so it sends an observe command.

Choose a route

shelly cover

A Gen2-or-later relay device in cover mode, calibrated on the device. Position covers only. One MQTT in node on <prefix>/#, no function nodes.

Zigbee2MQTT cover

A Zigbee cover paired with Zigbee2MQTT that reports a position. Today: the three function nodes from the Cover control example. Later: the zigbee2mqtt cover adapter.

For any other device, the controller’s neutral commands and readings are the contract to map to.

Check the result

Wire controller output 2 to a Debug node, then watch the shelly cover’s node status as well.

Read the outcome
What you seeWhat it means
shelly cover status “waiting for the device”No device message has arrived yet. Check the MQTT in topic and the broker.
shelly cover status showing a state and positionReports are arriving; it shows the cover’s last state and position.
Controller result not-calibrated / position-unknownA shelly cover cannot provide a usable position. Calibrate it on the device.
Controller result unavailableThe device is offline. No command is sent; it is read again when it returns.
No command reaches the deviceCheck that the MQTT out node uses the same broker and, after a shelly cover, has no topic set. For a shelly cover, check Enable MQTT Control; for the function nodes, check the friendly name in their topic.

Importable examples are in the package’s examples folder (Import → Examples in the editor): Shelly cover.json and Cover control.json. In each, injects stand in for the MQTT in nodes and a Debug node stands in for MQTT out. See also the README Covers section and the cover controller reference.
