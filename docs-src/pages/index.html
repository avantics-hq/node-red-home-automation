A few ideas carry through every flow

  • One command owner

    Policies ask for an outcome. A controller owns the device commands, so two parts of your flow do not fight over the same target.

  • Requests describe the result

    Send “open”, a position, or a lighting intent. The device path translates the controller’s commands into its protocol.

  • Evidence before completion

    Sending a command is not success. The controller waits for fresh observations; retries and failure paths have limits.

  • Recovery stays bounded

    Retries, timers, traces and failure paths remain finite, and a restart re-reads the devices rather than replaying commands.

  • Manual control stays yours

    A person’s change becomes ownership evidence, not something to correct immediately. The cover guide shows how automatic requests respect it.

Home Assistant is the panel, not the device path.

It can display state and send requests over MQTT. Controllers command and observe the devices directly, not through Home Assistant.

Use Home Assistant as the panel

Home Assistant is optional. Nodes you opt in publish their state over MQTT and announce their entities through MQTT discovery, and Home Assistant’s controls come back to the nodes as MQTT requests, carried out like any other request. The nodes still command and observe the devices directly, never through Home Assistant.

Wire each publishing node’s output to an MQTT out node and wire in a Status node watching MQTT out, so it announces itself once the broker has connected. The Home Assistant guide covers topics, entity names, availability and removing entities.
