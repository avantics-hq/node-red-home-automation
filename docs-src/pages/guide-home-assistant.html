Before you wire it

Home Assistant is optional. A node that publishes sends its state over MQTT and, with discovery on, announces its entities to Home Assistant. A control used in Home Assistant comes back to the node as an MQTT request on a /set topic, and the node carries it out like any other request. The devices are still commanded and observed directly, by the nodes, never through Home Assistant.

  • Publishing is opt-in, per node. Most publishing nodes have two settings: Publish state over MQTT and Home Assistant discovery, which needs Publish state. A new node starts with both off. Room lighting controllers and theatre state contracts saved before these settings existed keep publishing.
  • The theatre state contract always publishes its retained state; only Home Assistant discovery is a setting, off for a new node.
  • The house schedule MQTT node exists to publish, so it has only the Home Assistant discovery setting, ticked when you add it from the palette.
  • Give it an area. A node that publishes usually needs an Area, because its topics and IDs are named after it; without one the editor marks it invalid. The theatre state contract is the exception: with discovery off and a Base topic set, its area is optional. A room lighting controller with no area still controls its lights, but only with Publish state and Home Assistant discovery both off; with either on, or on a room saved before these settings existed (which counts as on), it fails as an invalid configuration.

Topics and IDs use the area in lowercase, with each run of spaces or other characters (anything but letters, digits, _ and -) as _. An area called “Upstairs Landing” publishes under home/upstairs_landing/…; “living-room” is unchanged. Names shown in Home Assistant keep the area as you typed it.

Keep state across restarts.

A node remembers what it published in its node context. With a file context store that record survives deploys and restarts, so old topics can be cleared reliably.

Wire publications out and requests in

Each publishing node has an output for its MQTT publications. Wire it to an MQTT out node. Where Home Assistant can change something, wire an MQTT in node on the node’s /set topics back into the node’s input.

The room lighting controller’s first output carries only its publications; its light commands leave through each light’s adapter. Flows that filter the first output by topic must pass the /control topics through. A light’s control sensor shows its availability as an attribute once its adapter reports it.

For the cover controller, <name> is its Name in topics, which has no default: give each cover in a room its own. For the house schedule MQTT node, <name> is the house schedule’s Name, house by default. Use one house schedule MQTT node per schedule: two would share the same topics and entities.

The motion lighting switch shows this node’s enable only: the shared global-enabled is not published, so motion can still be off everywhere while the switch shows on.

What Home Assistant sends

Home Assistant’s controls publish to the node’s /set topics. The node treats each one as a request: bounded, sent to the device by the node and confirmed from what the device reports. Nothing reaches the device from Home Assistant directly.

You can test a set topic without Home Assistant. This Inject node, wired into a circadian lighting policy whose area is “Study”, does what the circadian switch does:

Inject → circadian lighting policy · switch circadian lighting on
msg.topic = "home/study/circadian/set";
msg.payload = "ON";
return msg;
  • Circadian lighting policy: ON or OFF on circadian and sleep; a time (HH:MM or HH:MM:SS) on wake time and bed time. A time set this way lasts until you deploy the node with a different Wake time or Bed time. Set topics are read only while Publish state is on and the area is set; retained messages are ignored.
  • Theatre state contract: the activity selector sends a request with its own request ID to <base>/request, like any other activity request. Retained requests are inert.
  • Motion policy: ON/OFF on …/enabled/set and a delay of 0 to 86400 seconds on …/delay/set, as its area-enabled (true or false from a flow) and delay inputs do.
  • AVR controller: a volume in dB on …/volume/set. Sets within 0.3 seconds of each other are settled to the last, which becomes an ordinary absolute volume request. It waits for a power or source change in progress and is rejected with receiver-not-ready while the receiver is off.
  • Cover controller: OPEN, CLOSE or STOP on …/set, and, for a position cover, a position on …/position/set, carried out and confirmed like any other request.
  • House schedule MQTT: a time on the wake or bed time set topic changes the schedule for every circadian lighting policy that follows it. Retained messages and anything but a time are ignored.

Discovery prefix and entity names

Each node with discovery has a Discovery prefix setting, homeassistant by default, as in Home Assistant. Change it only if you changed the prefix in Home Assistant’s MQTT settings. Every discovery entry names this package and its version as its origin.

How IDs are named
NodeDevice, unique IDs and discovery topics
Room lighting controller or theatre state contract added from the paletteNamed after its Node-RED node ID (nrha_<node id>…), so renaming its area or display name updates the same entities.
Room lighting controller or theatre state contract saved before node IDsNamed after the area, exactly as before, so nothing changes for it in Home Assistant.
Occupancy fusion, motion policy, circadian lighting policy, AVR controller, cover controllerNamed after the node ID; they have no older entities. The circadian lighting policy clears the circadian, sleep, wake and bed entities a room published before 6.0 under the same area before it announces its own, so Home Assistant can give its entities the old entity IDs.
House schedule MQTTNamed after the house schedule, not this node, so a replacement node keeps the same entities.

Either way, the entity ID Home Assistant first gives an entity comes from the area, with - as _. Importing or pasting a node keeps its saved settings, including its ID scheme and publishing, so an older node restored from a backup keeps its area-named entities. Only a node added from the palette starts as new.

A theatre state contract added since node IDs suggests its Area to Home Assistant for its device, and Home Assistant creates an area of that name if none exists. With no area, its entity IDs come from its Display name and no area is suggested. One saved before node IDs needs an area for discovery.

Availability and the startup message

Each publishing node sends a retained online once the flows have started (and again at its startup message) and offline when it stops. Its Home Assistant entities follow it. With discovery on, it announces those entities at the same moments, just before online.

house schedule MQTThome/<name>/schedule/availabilitymsg.source = "startup"
  1. Wire a Status node watching MQTT out into each publishing node.

    Node-RED’s MQTT broker node connects after the flows have started, and drops anything it is given before then without a warning, so the announcement a node makes as the flows start is lost on a first start, a full deploy or a restart. A Status node whose scope is your MQTT out node passes on each of its status changes; when MQTT out shows “connected”, including after the broker reconnects, each node takes it as its startup message and announces again. Other status messages are ignored, so a Status node watching every node on the flow works too, as in the example flows. The startup messages below still work when you send them yourself.

  2. Set the broker node’s birth, close and will messages.

    The node’s own online and offline get through only when you deploy the node on its own (“Modified nodes” or “Modified flows”) while the MQTT connection stays up. On a full deploy, a restart or a shutdown, Node-RED stops the MQTT out node at the same moment and reconnects afterwards. So set the MQTT broker node’s Birth message to online, and its Close message and Will message (which covers crashes) to offline, all retained, on the same topic. With several publishing nodes, the broker can cover one of them.

The startup message does more than announce. The AVR controller discards stale observations and queries the receiver; the cover controller reads the cover again rather than trusting old state.

Availability is not readiness.

The theatre’s readiness (unknown, available, degraded or unavailable) is on <base>/readiness, shown as the “Readiness” sensor. <base>/availability carries only online or offline.

Remove entities

  • Switch discovery off to remove a node’s entities from Home Assistant at its next start.
  • Delete the node and deploy with “Modified nodes” or “Modified flows”: it clears its Home Assistant entities and retained state.
  • A full deploy (the deploy button’s default) stops the MQTT out node at the same moment, so the clearing never reaches the broker.
  • Disabling a node or its flow keeps its entities, so they come back unchanged when you enable it again.

To remove a node’s entities after a full deploy, or the entities of a flow you copied to another Node-RED (the copy’s nodes have new IDs, so new entities), delete the device in Home Assistant: Settings → Devices & services → Devices, open the device, then Delete. Home Assistant then clears its retained discovery entry itself.

Once the flows have started, and again at its startup message, a node clears any retained topic it published before and no longer does, for example after an area, base topic, discovery prefix or target change. It remembers what it published in its node context, which lasts across deploys and restarts only with a context store. Without that record, an occupancy, motion, receiver or house schedule MQTT node that publishes state still clears its own Home Assistant entities it no longer publishes, such as after you switch discovery off; it never clears topics another node could publish.

Moving an area between older room nodes.

A node that never gets a startup message keeps clearing its old topics at every start. To move an area from one older room node to another, send the old node a startup message, or delete it.
