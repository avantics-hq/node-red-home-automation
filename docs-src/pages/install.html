Before you start

The package declares what it needs in its package.json. Check both before you add it.

Requirements

Node-RED5.0.0 or newernode-red.version: >=5.0.0
Node.js24 or newerengines.node: >=24
Node-RED 5 runs on older Node.js than this package.

Node-RED 5 itself accepts Node.js 22.9, but this package needs Node.js 24 or newer. Check the Node.js version that runs your Node-RED before you add the package.

For the nodes that talk to devices or publish state, you also need an MQTT broker and an MQTT broker config node in Node-RED. Home Assistant is optional: it is a panel that shows state and sends requests, never the path to a device.

Add it from the palette manager

  1. Open the palette manager.

    In the Node-RED editor, choose Manage palette → Install.

  2. Search for the package.

    Search for @avantics/node-red-home-automation and install it.

  3. Find the nodes.

    They appear in the home automation category of the palette.

Add it with npm

Run this from your Node-RED user directory (usually ~/.node-red), then restart Node-RED:

Terminal · Node-RED user directory
npm install @avantics/node-red-home-automation

To pin a version, name it, then restart Node-RED. Each version is listed on the GitHub releases page.

Terminal · pin a version
npm install @avantics/node-red-home-automation@<version>
Check before updating.

This package is under active development. Pin the version you use, read the release notes and check your flows after an update. A major version can require changes to saved flows: the 6.0.0 notes list what to migrate.

Add it from a release tarball

Each GitHub Release also attaches the package tarball and its SHA-256 checksum. Check the checksum of the file you downloaded against the one in the release, then add it in either way:

  • In the editor, choose Manage palette → Install → Upload module and pick the tarball.
  • From your Node-RED user directory, install the tarball with npm and restart Node-RED.
Terminal · Node-RED user directory
npm install /path/to/avantics-node-red-home-automation-<version>.tgz

Set up a file context store

The nodes keep what they are doing in Node-RED’s node context. By default Node-RED keeps context in memory and deletes a node’s context whenever the node stops: on a full deploy, on a “Modified flows” deploy of its flow (which restarts every node in that flow, changed or not), on a “Modified nodes” deploy of the node itself, and on every restart.

Configure the file context store so it survives. In settings.js in your Node-RED user directory, set:

settings.js
contextStorage: {
    default: { module: "localfilesystem" }
},

Then restart Node-RED. The file store writes changes to disk every 30 seconds by default, so a change made just before Node-RED stops can still be lost.

Without a context store, after a node is redeployed or Node-RED restarts:

  • A room forgets which lights are held or manual. Every light an activity held, or a person set by hand, is back under the room’s control, so the next style restyles them.
  • Changes made at runtime go back to the node’s settings. For example motion lighting’s enable, vacancy delay and lux cutoff, a circadian policy’s circadian lighting, sleep, and wake and bed times, and the house schedule’s times, set from Home Assistant or a message.
  • The theatre starts its counts again. Its counters and operational SLO samples restart, and the activity controller no longer knows the current activity. At its next startup recovery it works it out from what the devices report; if no single activity matches, it switches to the recovery off activity.
  • Work in progress is not recovered. A motion off-timer that was running, or a theatre device change still being confirmed, is gone. The node starts afresh and goes by what it next observes.
  • Old retained topics are not cleared. A node can’t remember what it published, so after you change an area, base topic, discovery prefix or targets, the old retained topics and Home Assistant entities stay until you remove them yourself.

Connect the broker and send a startup message

A node that publishes state hands its MQTT messages to an MQTT out node on your broker. Two settings make that reliable.

  1. Send each publishing node a startup message once, a few seconds after a deploy.

    The example flows use an inject node set to fire once after 3 seconds. By then the MQTT broker node has usually connected; a message sent before it connects is dropped, along with the discovery and state it carried. The room example sends msg.lighting = {kind: "startup"}; each node’s reference page gives its own startup message.

  2. Set the broker node’s availability messages.

    Each publishing node sends a retained online once the flows have started and offline when it stops. On a full deploy, a restart or a shutdown, Node-RED stops the MQTT out node at the same moment, so those messages can’t get through. Set the MQTT broker node’s Birth message to online, and its Close message and Will message to offline, all retained, on the same availability topic; with several publishing nodes, the broker can cover one of them.

Removing a node’s entities.

Deleting a publishing node clears its Home Assistant entities and retained state only when you deploy with “Modified nodes” or “Modified flows”. After a full deploy, delete the device in Home Assistant instead: Settings → Devices & services → Devices, open the device, then Delete.

Configuration and security

The repository contains no home-network addresses, home coordinates or credentials. Device hosts and room coordinates are settings you provide where a node needs them.

The display mode controller stores its TV pre-shared key as a Node-RED credential. Keep credentials in Node-RED’s encrypted credential store rather than in flow fields or repository files.

Report a suspected vulnerability privately, using the process in SECURITY.md, not through a public issue.
